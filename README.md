# Technical Concept Breakdown

一个面向 AI 产品经理和技术决策者的 Codex Skill，用于快速拆解新模型、新架构、新算法、新协议和其他技术概念。

它不止回答“这是什么”，还会继续回答：

- 为什么它可能有效？
- 适合什么任务，不适合什么任务？
- 在产品系统中应该放在哪里？
- 官方 Benchmark 是否可信？
- 与现有方案相比，是否值得接入？

## 核心方法

```text
任务定义
  → 原理与证据
  → 能力边界
  → 系统定位
  → 数据与评测
  → 工程取舍
  → Go / Pilot / No-Go
```

Skill 使用五层框架：

1. **模型原理**：输入、关键机制、输出，以及相对旧方案的变化。
2. **能力边界**：擅长任务、成立条件、限制和失效点。
3. **系统架构**：组件在业务系统中的位置、上下游、路由、回退和人工节点。
4. **数据与评测**：Benchmark、Ground Truth、Baseline、分母、Cherry-picking 和独立复现。
5. **工程取舍**：效果、Calibration、延迟、Cost per Decision、可解释性、集成复杂度和锁定风险。

## 证据原则

优先使用官方论文、技术报告、模型卡、API 文档、原始 Benchmark 和独立复现。关键结论会区分：

- **事实**：来源直接支持；
- **推断**：由多个事实推导；
- **假设**：需要实验验证；
- **未知**：公开材料不足。

官方宣传、搜索摘要和模型生成的标签不会被自动视为独立证据或 Ground Truth。

## 调用方式

将本仓库复制到 Codex 的 Skills 目录后，可使用：

```text
使用 $technical-concept-breakdown 拆解一下这个新模型，并判断是否值得接入我的产品。
```

也可以直接提出类似问题：

- “帮我快速理解这个新架构，面试时怎么讲？”
- “这个模型和传统分类模型、LLM 的差异是什么？”
- “官方 Benchmark 提升很多，是否足以支持上线？”
- “请从系统位置、评测和工程成本判断这个方案。”

## 默认输出

默认交付包括：

1. 一句话定义与决策摘要；
2. 任务和研究边界；
3. 证据与置信度；
4. 五层技术拆解；
5. Baseline 对比；
6. 风险、未知和待验证项；
7. Go / Pilot / No-Go / Insufficient Evidence 建议；
8. 最小业务评测方案。
